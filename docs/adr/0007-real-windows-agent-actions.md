# ADR 0007: Real Windows actions with explicit results

Date: 2026-09-26. Status: Accepted for implementation; physical device acceptance pending.

This supersedes the all-command simulation decision in ADRs 0003 and 0005. `SimulateLock` and `SimulateNetworkIsolation` retain their original behavior. `LockWorkstation` and `IsolateNetwork` are distinct signed command types. Both require a local lab flag and an exact authorized device ID. The existing tenant checks, operator permission, confirmation, reason, expiry, nonce, signature and append-only completion audit remain mandatory.

Core depends on `ICommandExecutor` and `IAgentPolicyApplier`; OS code resides in Infrastructure. `AgentCycle` implements immediate telemetry and fetches the device's policy before applying it. A successful telemetry receipt requires a fresh sample and HTTP acknowledgement. Other unavailable actions fail explicitly, including the Core fallback. Durable failed and successful receipts retry without repeating the OS action.

Windows Service remains least privileged. A desktop companion, started with `--desktop-companion` in the logged-in user's session, handles notifications, workstation locking and idle settings. A local named pipe restricts access to trusted service identities and interactive users, checks client session and authenticates server identity. Only the active physical console session is selected; unattended and RDP-only devices fail clearly. Lock receipts require WTS session state confirmation, including independent verification by the Service. Notifications report the Windows API response without claiming the user read the message.

Service restart uses fixed PowerShell code with JSON input and the exact existing allow-list. It observes Stopped then Running through Service Control Manager. There is no remote script or arbitrary shell entry point. Service control requires an explicit local opt-in and delegated permissions.

Policy fetch is GET `/api/v1/agent/policy`, authorized as the authenticated Agent. PolicyService resolves the assignment and policy within the Agent tenant through its own store. Its DTO contains only policy ID, idle minutes and USB mode. Policy application requires a local opt-in and registry rights. Idle settings are read back through Windows; USB storage driver/write-protection registry values are read back. Already-mounted storage is not forcibly detached, and receipts state that reconnect/restart may be required. A configured assignment is not evidence of effective enforcement on attached hardware.

Firewall isolation is an explicit 30–60 second lab operation requiring elevation and a configured API IPv4 address matching DNS. Four dedicated block rules cover inbound/outbound IPv4 and IPv6, excluding the configured API IPv4 host. Before creating rules, it registers a SYSTEM scheduled recovery task with expiry and startup triggers. Recovery removes only the named rules and retains the task if removal cannot be verified. Disabled profiles or managed policies rejecting local rules cause failure. Active rules are read back; packet-level isolation and independent recovery still require real lab acceptance. DNS availability, additional API addresses, scheduler failure and privileged host tampering remain operational limits.

The shared HMAC key remains a production trust limitation: a compromised Agent holding it can forge commands. This change does not certify asymmetric signing/key rotation, database-level immutable audit, PostgreSQL behavior, or a live production rollout. See the [execution guide](../guides/real-agent-execution.md) for configuration and acceptance evidence.
